# Document Template

**説明** - 本文書が定義する対象と範囲を明記する。


## フロントマター規約

- 必須キーは `title`、`description`、`version`、`status`、`last_updated`、`lang`。
- フィールド順序は固定: `title` → `description` → `version` → `status` → `last_updated` → `lang`。
- `description` は日英併記。書式: `"日本語説明 / English description"`。
- `version` は semver 3桁（例: `"1.0.0"`）。
- `status` は `Stable`、`Draft`、`Deprecated`、`Archived` のいずれかを使用する。
- `last_updated` は `YYYY-MM-DDTHH:mm+09:00` 形式（秒なし）を使用する。
- 全値をダブルクォートで囲む。
- コメント行禁止。
- 本文に「最終更新：」行を記載しない（`last_updated` で管理）。

## 目次運用

- 目次セクション自体は定義可能だが、デフォルトでは記載しない。
- `H2` が4項目以上、または長文で章間参照が頻発する場合のみ目次を記載する。
- 目次を記載する場合は見出し変更時に必ず同期更新する。

## 見出し命名規約

- 見出しタイトルに「（必要時）」「（必要時のみ）」などの注記を含めない。
- 必要条件の注記は本文で記述し、見出しは簡潔な名詞句に統一する。

## 出典・参考情報表記規約
- 見出しは `## 出典・参考情報` を使用する。
- 参照情報は Markdown リンクを必須とする。
- ファイル間参照は Markdown リンクを使用し、同一ディレクトリの直接パス（ファイル名）で記載する（絶対パス記載を禁止）。
- 例: `[関連規定](http-error-code-reference.md)` を使用し、`/Users/...` のようなフルパスは記載しない。
- 参照行に「の根拠」という語を付与しない。
- `確認日:` は原則記載しない。更新時点の妥当性は `last_updated` で管理する。
- 書式は `- [参照名](URL) - 補足説明` を標準とし、補足説明が不要な場合は省略できる。
- 各章で外部情報に基づく記述を行う場合は、章末に `出典・参考情報: 項目名A、項目名B` を記載する。
- 章内に記載する項目名は、末尾の `## 出典・参考情報` に記載した参照名と一致させる。
- 出典・参考情報は、ドキュメントの種類に応じて項目分けが可能な場合、`## 出典・参考情報` 配下の `###` 見出しで分類を必須とする。
- 分類見出し名は内容に即して定義し、例として `### 情報・規格`、`### ツール公式ドキュメント` を使用できる。
- 章内では項目名のみを記載し、URLは末尾の `## 出典・参考情報` に集約する。

## ドキュメント制作時の内容検証要項

ドキュメント制作・精査・査読時に、以下の8観点を必ず確認する。

1. **対応技術の記述偏り：** 複数の技術・環境・プラットフォームを対応対象として列挙している箇所で、各対象の具体的な値・構文・設定・コマンドが書き分けられているか確認する。「A / B」と1行にまとめている箇所は、AとBの動作・値・名称が同一かを確認し、異なる場合は分離する
2. **「できないこと」の省略：** 推奨する機能・技術・手法が、対応対象の全てで利用可能かを確認する。非対応・条件付き対応（バージョン制限、有料版のみ、特定エディション等）を明記しているか確認する。型・フォーマット・サイズ等の暗黙の前提が全対象で成立するかを確認する
3. **代替手段の欠落：** 「非対応」「条件付き」と記載した箇所に、同等の目的を達成する代替実装パスが併記されているか確認する。運用パターンが複数存在する場合、各パターンに応じた差異が記載されているか確認する
4. **内部動作の不正確さ：** 機能・処理の動作記述が公式ドキュメントの該当セクションと一致するか検証する。「保持する」「変換する」「有効になる」等の動詞が内部の処理順序・保存形式・出力変換と正確に対応するか確認する。設定値・引数・モードによる動作分岐が記載されているか確認する
5. **デフォルト値の例外条件：** 「デフォルトで有効/無効」等の記述で、前提が崩れるケース（初期化方法、明示的フラグ、バージョン差異、特定構成、環境変数）が併記されているか確認する。確認対象（設定ファイル名、パラメーター名）が具体的に記載されているか確認する
6. **禁止事項と手順規定の混在：** 禁止事項リストが「何をしてはいけないか」のみで構成されているか確認する。代替手順が禁止事項内に埋め込まれていないか確認する。代替手順が必要な禁止事項に対して、判断根拠・段階的ステップ・前提条件・依存調査・事後確認を含む独立した手順規定が存在するか確認する
7. **出典の権威性不均一：** 全出典を一次ソース（公式ドキュメント、RFC、業界標準団体の公開文書）と二次ソース（ブログ、解説記事、個人サイト）に分類する。一次ソースが存在する領域で二次ソースのみを出典としている箇所を検出し、差し替え可能な場合は一次ソースに置換する
8. **同目的の複数手法の省略：** ある目的に対して記載された手法が1つのみの箇所で、公式ドキュメント上に複数の手法が存在するか調査する。複数存在する場合、各手法の適用場面が用途別に記載され、優先順位や使い分け基準が明記されているか確認する
